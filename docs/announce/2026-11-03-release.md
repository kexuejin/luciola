**First comment (post immediately after submitting):**

```text
Author here. I wrote this because I kept rebuilding the same broken thing: every
local-first app I shipped needed to find its own peers on a LAN, and every time I
reached for mDNS/Bonjour it worked on my desk and failed at the customer's site.
Local clipboard sync, LAN file drop, a phone hitting the desktop's dev server - all
of it hit the same three walls.

Why mDNS dies, in the three places I actually ship to:

1. Clash/Sing-box TUN mode. Enhanced mode installs routes for 0.0.0.0/1 and
   128.0.0.0/1, and in my setups the multicast and the limited broadcast end up on
   the TUN interface instead of the Wi-Fi one, where the proxy has no use for them
   and they are dropped. Discovery goes silent while plain unicast to the same peer
   keeps working. "Broadcast dead, unicast fine" is the signature.

2. Enterprise, hotel and campus Wi-Fi. Lots of APs drop client-to-client multicast
   (IGMP snooping pruning it, or multicast-to-unicast conversion never enabled), so
   224.0.0.251 never reaches the phone in the next room. mDNS becomes "sometimes
   works", which is worse than never working, because you ship it.

3. IPv6-only broadband (China Telecom/Unicom/Mobile handing out 2408:...). The LAN
   is one delegated /64 of GUA, with no RFC1918 range to key "this is local" on.
   Code that maps private-IP to LAN classifies every peer as WAN, and ff02::fb
   depends on the AP forwarding station-to-station multicast, which budget routers
   often do not.

So Luciola does not start from "join a multicast group and hope". It starts from
route tables and interface facts: per-NIC subnet-directed broadcast (192.168.2.255),
which has an on-link /24 and therefore wins longest-prefix-match against the TUN's
/1; a dual-stack engine that joins ff02::1 per NIC and matches peers by /64; NIC
scoring that drops Docker/VMware/Tailscale/Radmin/Windows-ICS adapters and filters
Clash's 198.18.0.0/15 fake-ip range; WSL2 host passthrough so the advertised address
is actually dialable; and manualPeers unicast as an explicit fallback for APs that
drop broadcast too. Then Happy Eyeballs races the candidates and the handshake runs
on the winning socket, so there is no race-then-dial gap.

The data plane is separate and closed by default: open discovery, deny-by-default
channels. Ed25519 identity, sha256 fingerprint, 6-digit on-screen PIN, Full/Partial/
unpaired trust levels. The channel is a SIGMA-style composition: X25519 ephemeral
ECDH, both sides sign the transcript with Ed25519, HKDF-SHA256, AES-256-GCM with
strictly increasing counters.

Different from ZeroTier/Tailscale? Different layer. Those give you an overlay
network with an account and a control plane, which is right when the peers are not
on the same link. This is the zero-server same-LAN layer, and it deliberately
classifies their virtual adapters instead of silently dialling into them; when you
do want to cross networks, you point manualPeers at the overlay address.

Honest status, because this is the part that gets people burned:

- The protocol is pre-audit. Vetted primitives (RustCrypto), custom composition,
  never externally reviewed. SECURITY.md says so and lists the review targets. Do
  not carry secrets over it before that review.
- Discovery frames are unauthenticated by design. Treat profile fields as display
  data; trust decisions belong to the trust store and the secure channel.
- The secure listener serves one session at a time; a second peer queues in the
  backlog. Per-peer sessions (or the tunnel) if you need concurrency.
- iOS: the Swift path is simulator-verified. The Kotlin/Native path runs under
  iosSimulatorArm64Test in the simulator; a physical-device run is still missing.
- Node binding builds from source; no npm package yet.
- 0.9.0 is on crates.io (seven crates) and Maven Central; the iOS xcframework is on
  the v0.9.0 tag.

Try it without writing code:

    cargo install luciola-cli
    luciola-cli ip        # interfaces, TUN detection, candidate addresses, QR
    luciola-cli scan      # live peer radar
    luciola-cli beacon --name "my-laptop" --qr

Rust: luciola = "0.9.0". Gradle: io.github.kexuejin:luciola:0.9.0.
Docs: https://docs.rs/luciola and docs/INTEGRATION.md in the repo.

What I would most like from HN: failure reports where discovery still dies. The
useful ones say which router/AP model, whether broadcast, multicast and unicast each
work, and what luciola-cli ip prints for candidates (it prints no secrets). That last
detail is how the WSL2 and ZeroTier fixes got found.
```

commands stay readable. Do not put the GitHub URL in the comment body; the title

**Body:**

```text
Luciola is a LAN discovery and secure-connection engine for local-first apps, and
0.9.0 went out today on crates.io (seven crates) and Maven Central.

The problem it exists for: mDNS/Bonjour is the obvious answer for "find the other
device on my network", and it fails in three specific real-world conditions -
Clash/Sing-box TUN proxy mode, Wi-Fi networks whose APs drop client-to-client
multicast, and IPv6-only broadband where the LAN is a delegated GUA /64 with no
RFC1918 range to key on. I wanted a discovery layer that treats those as the normal
case rather than the exception.

What is in 0.9.0:

- Crates: luciola (engine, secure channels, trust), luciola-ip (RFC scope taxonomy,
  /64 GUA matching, 198.18.0.0/15 TUN range filter, no_std), luciola-net (NIC
  scoring, virtual-adapter filtering, subnet-directed broadcasts), luciola-proto
  (versioned wire envelopes, jitter/dedup), luciola-transfer (chunked file transfer
  with absolute-offset writes and contiguous-prefix ACKs), luciola-tunnel (mux with
  TCP/UDP forwarding), luciola-cli (ip / scan / beacon / agent / forward / ports).
- Discovery: dual stack. Per-NIC subnet-directed broadcast on IPv4 (an on-link /24
  beats a proxy TUN's 0.0.0.0/1 on longest-prefix match) plus ff02::1 link-local
  multicast on IPv6, with unicast replies. NIC scoring filters Docker/VMware/
  Tailscale/Radmin/ICS, and WSL2 gets host-address passthrough.
- Connection: Happy Eyeballs racing across every candidate subnet, then the handshake
  runs on the winning socket.
- Channels: Ed25519 identity, sha256 fingerprint, 6-digit comparison PIN, tiered
  trust store, TOFU capture, reconnect with backoff, bounded queues. The handshake is
  SIGMA-style (X25519 + Ed25519 transcript signatures + HKDF-SHA256 + AES-256-GCM)
  and is a custom composition.
- Bindings: KMP for Android/JVM/iOS (io.github.kexuejin:luciola on Maven Central,
  arm64 .so inside the AAR), Swift + xcframework on the v0.9.0 GitHub release, and an
  N-API layer for Node/Electron built from source.

Known limitations, so nobody finds them the hard way:

- The protocol is pre-audit. SECURITY.md documents the inventory and the two review
  targets; until that review happens, treat it as a transport for non-secret data.
- Discovery is unauthenticated by design; data planes are deny-by-default.
- The secure listener accepts one session at a time (backlog queuing, not parallel
  peers). The tunnel is the way to multiplex more.
- The Node package is not on npm and its package metadata is darwin/arm64 only.
- iOS: Kotlin path runtime-verified in the simulator, physical device still
  outstanding; Swift path is simulator-verified.
- No benchmarks here. If you want one, I would rather add it with you than quote a
  number I cannot reproduce.

License is MIT OR Apache-2.0. Repo, docs and changelog:
https://github.com/kexuejin/luciola
https://crates.io/crates/luciola
https://docs.rs/luciola
```

**正文:**

```text
做本地优先应用时反复踩同一个坑：局域网发现只要用 mDNS/Bonjour，在我的机器上永远
能用，到用户那里就时好时坏。攒了三种可复现的失败场景，最后写成了一套 Rust 引擎
Luciola（萤火），0.9.0 今天发到 crates.io 和 Maven Central。这里只讲技术，不讲情怀。

三种失败模式的机制：

1）Clash / Sing-box 的 TUN 增强模式。它装 0.0.0.0/1、128.0.0.0/1 两条路由，受限广播
和 mDNS 的组播在我这边会落到 TUN 网卡上，代理对它们没有处理逻辑，直接丢掉。典型
现象是「广播全死、单播正常」——看到这个组合基本就可以怀疑 TUN。

2）企业 / 酒店 / 校园 Wi-Fi。很多 AP 不转发 STA 之间的组播（IGMP snooping 把它剪了，
或者 multicast-to-unicast 根本没开），224.0.0.251 到不了隔壁房间的手机。mDNS 于是变成
「有时候能用」，这比一直不能用更坑，因为你会把它发出去。

3）国内宽带的 IPv6-only 局域网。运营商给的是 2408: 开头的 GUA，一个委派的 /64，
没有 RFC1918 可以用来判断「这是内网」。把私网地址等同于局域网的代码会把对端判成公网；
而 ff02::fb 依赖 AP 转发 STA 间组播，廉价路由器经常不转。

Luciola 的做法不是「加个组播组然后祈祷」，而是从路由表和网卡事实出发：

- 每块物理网卡算子网定向广播（192.168.2.255）。它有一条 on-link 的 /24 路由，最长前缀
  匹配下优先级高于 TUN 的 /1，所以能绕开代理。
- 双栈：IPv4 走定向广播，IPv6 每个网卡加入 ff02::1，按 /64 前缀判断同局域网，单播回复。
- 网卡打分：过滤 Docker/VMware/Tailscale/Radmin/Windows 热点的虚拟网卡，过滤 Clash
  fake-ip 的 198.18.0.0/15；WSL2 做宿主真实 IP 穿透，保证宣告出去的地址真的能拨。
- manualPeers 单播兜底：AP 连广播都不转的时候，还有一条明示的退路。
- Happy Eyeballs 竞速，握手直接在胜出的 socket 上完成，没有「竞速完再重连」的间隙。

数据面是另一回事：发现开放，数据面默认拒绝。Ed25519 设备身份、sha256 指纹、屏上 6 位
比对 PIN、分级信任库；信道握手是 SIGMA 式组合（X25519 + Ed25519 全 transcript 签名 +
HKDF-SHA256 + AES-256-GCM，递增计数器防重放）。

现状，按可信度分层说清楚：

- 0.9.0 已发 crates.io（七个 crate）和 Maven Central；iOS xcframework 在 v0.9.0 的
```

## 6. 掘金（中文长文）

**标题（不夸张，直接给问题）:**

```text
Clash TUN 打开后 mDNS 为什么就死了：局域网发现的三种真实失败模式
```

**开头（可复制正文前 3 段）:**

```text
我在做局域网剪贴板同步和直连文件传输时，遇到过同一个问题三次：mDNS/Bonjour 在我
的开发机上永远能用，到用户那里就时好时坏，而「时好时坏」是最难排查的状态——它不报错，
只是慢，或者某些设备互相看不见。

后来我把这三种场景一个个抓到可复现，写成了一套 Rust 引擎 Luciola（萤火），0.9.0
刚发到 crates.io 和 Maven Central。这篇文章不复述 API，只讲三件事：mDNS 到底在哪一步
死的、从路由表和多播语义上怎么确认、以及在应用层还能做什么补救。

先给结论：绝大多数「局域网发现玄学」，都能收敛到三类原因——路由被代理 TUN 抢走、
AP 不转发 STA 间组播、以及 IPv6-only 宽带下没有私网地址可依据。下面逐条拆。
```

**结构提纲:**

1. **现象与最小复现**
   - 一个 20 行的 mDNS 服务发现 demo；开/关 TUN 各跑一次，记录「广播死、单播活」。
   - 如何用 `luciola-cli ip` 的输出判断当前机器上哪块网卡被 TUN / 虚拟网卡污染。
   - 区分三类症状：完全没包、有包但没回复、有回复但地址不可拨。

2. **路由表视角：0.0.0.0/1 与最长前缀匹配**
   - 为什么 TUN 增强模式装的是 `0.0.0.0/1` + `128.0.0.0/1` 而不是默认路由。
   - 受限广播为什么没有前缀锚点，容易跟着默认/TUN 路由走掉。
   - 子网定向广播为什么活着：`on-link` 的 `/24` 在最长前缀匹配里赢过 `/1`。
   - 配图建议：`netstat -rn` 前后对比截图（本地生成，不贴机器路径）。

3. **多播语义：AP 到底转不转**
   - 224.0.0.251 / ff02::fb 是链路本地组播，依赖 AP 的 STA 间转发。
   - IGMP snooping、multicast-to-unicast 转换、AP isolation 三个开关的组合。
   - 为什么「同网段但不同 AP」时 mDNS 会随机失效。
   - 实测边界：双端都正确入组、AP 依然不投递的情况存在（本项目 docs/INTEGRATION.md
     §8 记录过这个警告），所以多播只能是零配置路径，不能是唯一路径。

4. **IPv6-only 宽带：没有私网地址可用**
   - 运营商委派 GUA `/64`（2408: 开头），没有 NAT、没有 RFC1918。
   - 把「私网地址 = 局域网」的代码在这是错的；正确依据是前缀长度与作用域。
   - ff02::1 链路本地多播、单播回复按地址族选出口 socket。
   - 边界：IPv6 多播同样吃 AP 行为，跨网段必须叠加单播。

5. **应用层还能做什么（Luciola 的取舍）**
   - 网卡打分与虚拟网卡过滤（Docker/VMware/Tailscale/Radmin/ICS）、Clash fake-ip
     `198.18.0.0/15` 过滤、WSL2 宿主穿透。
   - manualPeers 单播兜底的定位：不是银弹，是「广播不可靠」时的显式配置。
   - Happy Eyeballs 竞速 + 握手落在胜出 socket 上。
   - 端口规划：同机多产品用 16 端口块，`tunnel = channel + 1`，避免互相抢 17878。

6. **安全边界别和发现问题混在一起**
   - 发现开放、数据面默认拒绝；Ed25519 身份、指纹、6 位 PIN、分级信任。
   - SIGMA 式握手：X25519 + Ed25519 transcript 签名 + HKDF + AES-256-GCM。
   - 必须写清楚：这是 pre-audit 的自研组合，原语成熟不等于组合经过审计。

7. **已知限制（写在正文里，不藏在脚注）**
   - 安全监听单槽、iOS Kotlin 路径仅模拟器验证、Node 包未发 npm 且仅 darwin/arm64。
   - 0.9.0 起端口冲突不再静默回落到临时端口，而是显式 `bind_failed`。

8. **怎么在你的环境里验证**
   - `cargo install luciola-cli` → `luciola-cli ip` / `luciola-cli scan` / `luciola-cli beacon`。
   - 三类日志：候选地址、广播目标非空、对端可拨性。
   - 结尾征集失败案例：附路由器型号与三种传输各自的通断。

## 7. 知乎（长文提纲，不是空话）

**问题式标题:**

```text
为什么一开 Clash 的 TUN 模式，同一个 Wi-Fi 下的设备就互相找不到了？
```

**开头（200 字左右，先给可验证的结论）:**

```text
这不是玄学，通常是三件事之一：代理的 TUN 网卡把 mDNS 的组播/受限广播吃掉了；接入点
不转发 STA 之间的组播；或者你的局域网是 IPv6-only 的 GUA 网段，而代码还在用「私网
地址」判断内外网。判断顺序建议是：先看路由表，再看组播能不能过 AP，最后才怀疑应用
代码。下面按这个顺序给可复现的检查方法，以及应用层能做的补救——包括我为此写的开源
引擎 Luciola（Rust，MIT/Apache-2.0，pre-audit）在每一步的取舍。
```

**提纲（长文骨架，每节 400–800 字）:**

1. **先排除误判：三种「找不到」不是一回事**
   - 完全收不到信标 / 收到信标但连不上 / 连上了但地址不可拨。
   - 各自的最小检查命令与判定表。

2. **路由表：TUN 增强模式到底改了什么**
   - `0.0.0.0/1` + `128.0.0.0/1` 取代默认路由的原理，为什么是两条半段而不是一条。
   - 最长前缀匹配：`/24` on-link 为什么还能活着，受限广播为什么容易掉进去。
   - 给出前后 `route` / `netstat -rn` 对照（本地截图，别贴个人路径）。

3. **组播：AP 是黑盒，但可以测**
   - 224.0.0.251 与 ff02::fb；IGMP snooping、multicast-to-unicast、AP isolation。
   - 一个 10 分钟的双机对测流程：A 发组播、B 抓包，换 AP/换频段复测。
   - 结论句要克制：多播不是不能用，是不能当唯一路径。

4. **IPv6-only 宽带为什么让老代码失效**
   - GUA `/64` 委派、没有 RFC1918、作用域判断应该看前缀而不是「像不像私网」。
   - ff02::1 入组与单播回复；跨网段必须叠加单播。
   - 引用本项目文档里「双端入组但 AP 不投递」的实测警告，避免把多播说成可靠。

5. **应用层的四种补救，以及各自的代价**
   - 子网定向广播（代价：仍受 AP 隔离影响）。
   - 单播对账 / manualPeers（代价：需要一条发现以外的通道或手工配置）。
   - 虚拟网卡过滤与网卡打分（代价：规则要跟着新软件更新）。
   - 双栈 + 前缀匹配（代价：实现复杂度，且 IPv6 多播同样吃 AP 行为）。

6. **连接层：发现了之后怎么连**
   - Happy Eyeballs 竞速；握手落在胜出 socket；IPv6 链路本地要补 scope id。
   - 为什么「先竞速再重连」会留下一个用户能感知的间隙。

7. **安全边界：发现是开放的，数据面不是**
   - 这一节的写法要防止读者误读：发现帧不认证 ≠ 数据不加密。
   - Ed25519 / sha256 指纹 / 6 位 PIN / 分级信任；SIGMA 式握手的组成。
   - 明确写「pre-audit」的含义：原语成熟、组合未经外部审计、评审清单在 SECURITY.md。

8. **诚实收尾：还没解决的部分**
   - 单槽监听、移动端后台冻结、iOS 真机未验证、Node 包未发布。
   - 这些不是道歉，是给读者的预期管理；局域网问题本来就没有一键方案。

## 11. Deliberately not written (and why)

These are the sentences that would have made the copy stronger and the project less
trustworthy. Keep them out:

- No benchmark numbers (latency, throughput, discovery time). The repo publishes
  none, and a number without a reproducible harness is a liability.
- No user counts, download counts, star counts.
- No "audited", "security-reviewed", "production-ready", "battle-tested". SECURITY.md
  says pre-audit; 0.x says the API still moves.
- No "Android library". The KMP library is one surface of a Rust core; Swift and Node
  are peers, and the README's own lesson (`AGENTS.md` §8) is that Android-only framing
  misleads iOS and desktop readers.
- No "replaces ZeroTier/Tailscale". Different layer; the honest claim is "same-LAN
  discovery with no server, and it coexists with overlays".
- No npm install line. `@luciola/core` returns 404 on the registry.
- No "works on all routers/APs". The docs themselves record an AP that drops
  station-to-station multicast even when both ends joined the group correctly.
- No iOS physical-device claim; no "verified on iPhone".
- No hidden-machine paths (personal volume or home-directory paths). `AGENTS.md` §5.
